# zimt

A small compute runtime for [Slang](https://shader-slang.org) kernels on
Metal, CUDA and Vulkan, written in Zig.

Kernels take buffers as device addresses, not bindings: a buffer
parameter is `RO<T>` or `RW<T>` (from zimt.slang), a 64-bit pointer. A
kernel's parameters are one block of addresses and scalars,
laid out as a C struct and identical on every backend: Vulkan pushes it as
push constants (buffer device addresses), Metal binds it at index 0
(`gpuAddress`), and CUDA passes it as the kernel parameters. There are no
descriptors, binding numbers or buffer indices.

Its build runs `slangc -reflection-json` once per kernel and turns the
result into a Zig binding: a comptime description of the kernel with a
typed `Args` struct: buffers are `zimt.Buffer(T)` with `T` the element
(`RO<float2>` is `Buffer([2]f32)`, read from the SPIR-V), so a mismatched
buffer doesn't compile. Scalar and vector elements are laid out as in C
and Zig on every backend: a `float3` is `[3]f32`, 12 bytes apart. This is checked: bindgen
fails if the Metal and SPIR-V reflections disagree, and at comptime each
element's `@sizeOf` must equal the reflected stride and each parameter
must fit its reflected slot. A dispatch takes its arguments by name and
packs them at comptime-known offsets; when only one backend is compiled
in, the backend switch folds away too.

```zig
const zimt = @import("zimt");
const kernels = @import("my_kernels"); // generated by zimt.addKernels

const dev = try zimt.Device.open(allocator, .metal);
defer dev.close();
const saxpy = try dev.kernel(kernels.saxpy);
defer dev.release(saxpy);

const x = try dev.allocInit(f32, xs);
const y = try dev.allocInit(f32, ys);
try dev.dispatch1d(saxpy, n, .{ .x = x, .y = y, .a = 2.0, .n = n });
try dev.download(y, 0, ys);
```

The kernel behind it is plain Slang. Entry-point `uniform` parameters
become `Args` fields, in declaration order:

```slang
import zimt;

[shader("compute")]
[numthreads(32, 1, 1)]
void saxpy(uint3 tid: SV_DispatchThreadID,
           uniform RO<float> x,
           uniform RW<float> y,
           uniform float a,
           uniform uint n)
{
    uint i = zimt_index(tid); // not tid.x: see dispatch1d below
    if (i >= n) return;
    y[i] = a * x[i] + y[i];
}
```

## Using it from a build

Add a dependency to your `build.zig.zon`, then use the helpers from your
`build.zig`:

```zig
const zimt = @import("zimt");

const metal = zimt.resolveMetal(b, b.option(bool, "metal", "Metal backend"), target.result.os.tag);
const vulkan = b.option(bool, "vulkan", "Vulkan backend") orelse false;
// `target` is needed when Vulkan is on (translate-c of the Vulkan headers).
const dep = b.dependency("zimt", .{ .target = target, .metal = metal, .vulkan = vulkan });
const kernels = zimt.addKernels(b, .{
    .zimt = dep,
    .sources = b.path("shaders"),             // <entry>.slang
    .generated = b.path("shaders/generated"), // checked-in .metal, .spv + reflection
    .entries = &.{.{ .name = "saxpy" }},
    .metal = metal,
    .vulkan = vulkan,
});
exe_mod.addImport("zimt", dep.module("zimt"));
exe_mod.addImport("my_kernels", kernels);
b.step("shaders", "Regenerate MSL, SPIR-V + reflection").dependOn(zimt.addRegenerate(b, .{
    .zimt = dep, // for zimt.slang
    .sources = b.path("shaders"),
    .generated_dir = "shaders/generated",
    .entries = &.{.{ .name = "saxpy" }},
}));
```

- **MSL, SPIR-V and their reflection are checked in**, so Metal and Vulkan
  builds need no Slang install. Run `zig build shaders` after editing a
  kernel; it needs `slangc` and `spirv-val`, which checks the SPIR-V
  against Vulkan 1.2. Bindgen checks that the Metal and SPIR-V reflections
  agree (parameters, layout, thread-group size).
- **Kernels compile to `.metallib`** at build time with IEEE math, for
  macOS 13 by default (`macos_min`, `fast_math`).
- **CUDA (`.cuda = true`)** compiles PTX with `slangc`, which needs NVRTC.
  Each `Device` is a non-blocking stream on the GPU's primary context, so
  several devices in a process share it and overlap their work.
  `libcuda` is loaded at run time (`libcuda.so.1`, then NixOS's
  `/run/opengl-driver/lib`; `nvcuda.dll` on Windows), so without a driver
  `Device.open` returns `BackendUnavailable`. The API comes from NVIDIA's
  redistributable `cuda.h` and `cudaTypedefs.h` through translate-c (a
  lazy package, fetched only with `.cuda`), and entry points resolve with
  `cuGetProcAddress`, so drivers from CUDA 12 on.
- **Vulkan (`.vulkan = true`)** embeds the checked-in SPIR-V. Its API
  bindings are translate-c output of `vulkan_core.h` from Khronos'
  Vulkan-Headers, a lazy package dependency fetched only when Vulkan is on.
  The loader is `dlopen`ed (`libvulkan.so.1`, `vulkan-1.dll`). musl
  targets can't load it, so `-Dvulkan` fails the build there.
- **Kernels `import zimt;`**, which zimt adds to the Slang include path
  (zimt's `src/slang`), for `RO`/`RW`, `zimt_index` and `zimt_groups`.
- **One entry point per kernel**: `.name` compiles `<name>.slang`'s
  `<name>`; `.source` and `.entry` pick another file and a specialized
  generic (`fft_pass<Radix16>`), so one generic kernel can be several.
  `.defines` (`&.{"REAL=double"}`) builds one source more than once.
- **`.precise = true`** builds with `-fp-mode precise`: no contraction
  into FMAs, so f64 kernels can follow a CPU's operation order exactly.
- **Buffer elements may be structs** declared in Slang. bindgen emits
  each as an `extern struct` with explicit padding, its offsets checked
  at comptime: one type (`kernels.Span`) when every backend lays it out
  alike, else `kernels.Job(b)` per backend (Vulkan and Metal as Slang's
  scalar layout, CUDA aligning `float2`/`float4` to 8/16), and the
  kernel's `Args(b)` follow; load such a kernel with
  `dev.kernelOn(b, K)` from code instantiated per backend. Host data is
  written in the device's layout, without repacking.
- **f64 kernels** (`.float64 = true`, for kernels using `double`) have no
  Metal build or reflection; their binding has `float64 = true`, and
  `Device.kernel` returns `Unsupported` unless `Device.float64`: on CUDA,
  and on Vulkan with `shaderFloat64` (which zimt then enables).
  `ZIMT_VULKAN_NO_FLOAT64=1` hides it, to test the fallback. Metal has
  no f64. Slang generics turn `T(literal)` into a float first, so a
  `REAL` define keeps double constants exact where generics would not.
- **The `zimt` module has no target of its own** and takes the target of
  the module that imports it.

`resolveMetal` probes `xcrun metal --version` with a 10 s timeout, run in
its own process group, before it enables Metal. An explicit `true` fails
the build if the toolchain does not work; the default leaves Metal out
with a warning. All `xcrun` calls use `/usr/bin/xcrun` with
`DEVELOPER_DIR` and `SDKROOT` unset, so a nix shell's SDK cannot shadow
Xcode.

## Semantics

- **Arguments:** `zimt.Buffer(T)` for `RO<T>` / `RW<T>` with `T` a
  scalar, vector or struct of them (f64 in `float64` entries), and `u32`,
  `i32`, `f32` or `f64` for scalar uniforms. Bindgen rejects other parameter types, including
  `StructuredBuffer`s and bare pointers. Atomics go through the pointer:
  `InterlockedAdd(count.p[i], 1)`.
- **Ordering:** dispatches and transfers run in the order they are
  enqueued, and each sees the previous ones' writes.
- **Fences:** `submit()` returns a fence, a point on a monotonic
  timeline. Each submission is a committed command buffer on Metal, a
  recorded event on CUDA, and a command buffer signalling a timeline
  semaphore on Vulkan.
  - `wait(fence)` blocks until exactly the work up to that fence is done;
    later submissions keep running.
  - `done(fence)` checks without blocking.
  - `submit()` with nothing new enqueued returns the latest fence again.
  - `synchronize()` is `wait(submit())`.
  - Completed submissions are retired oldest first, and a failure is
    reported by the `wait`, `done` or `submit` that retires it.
- **Buffers:** `dev.alloc(T, usage, len)` returns a `Buffer(T)` of `len`
  elements; `allocInit(T, data)` uploads too. `upload`, `download` and
  `zero` take element offsets and slices of `T`. Usage is comptime:
  - `.device`: read and written by kernels;
  - `.readback`: written by kernels, read by the host. Host-visible
    memory the device writes directly (mapped page-locked memory on CUDA,
    host-visible cached memory on Vulkan), so `download` is a memcpy once
    the device is done. Not for data kernels re-read, nor for atomics.
- **Memory** is zimt's, the same on every backend. Backends provide
  blocks; `alloc` suballocates shared blocks (64 MiB for `.device`) per kind
  with a buddy allocator (power-of-two classes from 256 B, so every
  allocation is 256-byte aligned; `Buffer.sub` views need not be), and a buffer larger than a block gets one of its
  own. A buffer's `mem` is a `zimt.Allocation` (block, offset, size),
  and kernels see its `address()`. `free` defers until the work that may use
  the buffer has completed. A large buffer's block is a whole number of
  block sizes, so nearby sizes reuse it. Emptied blocks are kept for reuse up
  to an eighth of the device's budget per kind (at least
  `Device.spare_size`, 256 MiB). A `zimt.Arena` (`dev.arena()`) frees its
  buffers together.
- **Budgets:** before taking another block, zimt checks the backend's
  budget for that kind of memory (`VK_EXT_memory_budget`, `cuMemGetInfo`,
  Metal's `recommendedMaxWorkingSetSize`) and `Device.memory_limit`; over
  it, it waits for deferred frees and drops spare blocks, then fails with
  `OutOfMemory` rather than oversubscribe. `dev.budget(kind)` reports it.
- **Host mapping:** `Buffer.host()` is set where the backend mapped the
  block: always on Metal (shared storage), for `.readback` elsewhere
  (on Vulkan unless no host-visible type can back it), and for `.device` on Vulkan where mapped memory is the
  device's main memory (see [Vulkan](#vulkan)).
- **Transfers:** `upload` and `zero` are enqueued like dispatches
  (`upload` copies its data before returning); `download` waits for
  everything before it. Mapped buffers wait for the device, then
  `memcpy`. Others go through a 32 MiB staging block (page-locked on
  CUDA) with enqueued copies; `zero` fills whole words and uploads the
  ragged ends.
- **Backend interface:** `open`/`close`, `kernel`/`release`,
  `blockAlloc`/`blockFree` (with each block's device address), `budget`,
  `copy` and `fill` between block ranges, `dispatch` (direct or indirect
  groups), `submit`/`finish`. Everything else lives in `root.zig`.
- **`dispatch1d`** launches at least `n` threads. Up to 32768 groups it is
  a single row; beyond that it folds into rows of 32768 groups (Vulkan
  only guarantees 65535 groups per dimension), so kernels take their
  index from `zimt_index(tid)` rather than `tid.x`, and
  bounds-check it.
- **Indirect dispatch:** `dispatchIndirect(k, groups, i, max, args)` runs
  the groups a kernel wrote to `groups[i]` (a `Buffer([3]u32)`), at most
  `max` per dimension, without the host reading them; `dispatchIndirect1d`
  pairs with `zimt_groups(n, threads_x)` in a kernel and takes the most
  threads `n` can be. Vulkan and Metal read the groups on the device. The
  CUDA driver API has no indirect launch, so CUDA launches `max`: kernels
  must bound-check against the count they read, not just the grid.
- **Access:** each buffer parameter's access (`read` for `RO`,
  `read_write` for `RW`) is in `K.params`. Vulkan uses it to order
  commands (see [Vulkan](#vulkan)); Metal makes the buffers resident with
  it; CUDA orders dispatches itself.
- **Threads:** a `Device` is not thread-safe, so serialise access to it.

## Vulkan

Vulkan 1.2 devices with timeline semaphores, buffer device addresses and
scalar block layout (Slang's layout of structs behind pointers)
qualify; others are skipped. One compute queue, compute-only if there is
one.

- **Device:** the first discrete GPU, then integrated, then others, CPU
  implementations last. `ZIMT_VULKAN_DEVICE=<index|name substring>`
  overrides it (e.g. `llvmpipe` for Mesa's lavapipe). `Device.name()` is
  `<device> (<driver>)`.
- **Memory:** each block is one `VkDeviceMemory` with one `VkBuffer`
  over it, addressed with `vkGetBufferDeviceAddress`. Where
  device-local, host-visible memory is most of the device's memory (APUs,
  ReBAR, CPU drivers), blocks live there and are mapped, as on Metal.
  Otherwise (e.g. a 256 MiB BAR window without ReBAR) they are
  device-local and transfers are staged; a full mapped heap also falls
  back to device-local. `ZIMT_VULKAN_NO_HOST_MAP=1` forces staging.
- **Validation:** `ZIMT_VULKAN_VALIDATION=1` enables
  `VK_LAYER_KHRONOS_validation` with synchronisation validation. Errors
  are logged and fail the next `submit`, `wait` or transfer; a missing
  layer fails `Device.open` loudly (set `VK_LAYER_PATH`). Accesses through
  device addresses are invisible to synchronisation validation; zimt's
  own barriers (below) cover them.
- **Barriers** come from each kernel's reflected accesses, resolved at
  comptime into the buffers it reads and writes. A command gets a barrier
  only if it reads or writes bytes written since the last barrier, or
  writes bytes read since then (buffers sharing a block don't conflict;
  indirect groups count as reads);
  independent commands, copies and fills run back to back. Every
  submission ends with a full barrier.
- **Releasing a kernel** while submitted work is outstanding waits for
  the queue first.
